# Novora 数据提交与同步演进方案（可持续性与未来规划）

基线：`novora-main-latest`，版本 `2.8.0`，分支 `fix/audit-log-zh`（干净工作树）。
本方案只做分析与规划，代码改动按「阶段 A」起分批落地。

## 一、问题定性

现状不是「服务端权威合并」，而是**单文档整体替换 + 单版本乐观锁 + 客户端三方合并**：

- 存储：`exam_data` 单行 JSONB（`id = 1`），承载 `items/title/majors/weekly_plans/grades/classes/...`
  （`api/_exams/db.ts` 建表处）。
- 写入：任一改动整行 `UPDATE`（`api/_exams/routes/examDataRoutes.ts`），
  并发保护是整行 CAS：`WHERE id = 1 AND updated_at = baseUpdatedAt`。
- 冲突：版本不等即 `409 DATA_CONFLICT` + 回传**整份** `remote`；合并逻辑只在客户端
  （`src/utils/examMerge.ts`、`src/services/examOutbox.ts`、`src/hooks/admin/*`）。
- 写入节流：全局写槽 900ms（`api/_exams/db.ts` 的 `GLOBAL_WRITE_MIN_INTERVAL_MS`）
  叠加每 key 8 写/10s（`api/exams.ts`）。
- 读取：整份快照，靠 ETag / 版本化边缘快照省流量，没有增量拉取。

由此产生四个可量化的成本：写放大（每次提交全部域）、冲突粒度粗（跨域互相顶掉）、
写入串行（全局槽 + 每 key 配额）、读放大（整份 + 冲突时再回整份）。

另外有一处纯冗余：`items`/`title` 是 `majors[activeMajorId]` 的镜像，每次提交把最大的一块数组传两遍。

## 二、五条不变式（任何阶段都不得破坏）

1. **读契约冻结**：`exam_data` 快照仍是教室大屏、ClassIsland 插件、设备心跳的读源，字段语义不变。
2. **离线能力冻结**：本地优先 + outbox + 断网可编辑，写入不得静默丢弃。
3. **权限与审计冻结**：所有写仍经 `requireActor` + 权限校验 + `writeAudit`。
4. **数据边界冻结**：作者端不读考试正文。
5. **可独立发布与回滚**：每个阶段单独可上、可回，不要求跨阶段同时上线。

## 三、目标架构

写入侧从「提交结果快照」逐级演进到「域级修订 → 记录级命令」；存储侧把 `exam_data`
定位为读模型（投影），列表型域逐步关系化；读取侧保持整份 + ETag 兼容，另加增量拉取。
核心是**读写解耦**：写可以越来越细，读永远还能一次拿到完整快照。

```text
写入  ：整份快照  →  域级提交（只发改动域）  →  记录级命令（upsert/delete + 版本 + 幂等键）
存储  ：单行 JSONB（权威）  →  单行 JSONB（读模型）+ 域修订号  →  + 记录表（权威）+ 快照投影
读取  ：整份 + ETag  →  整份 + ETag + since 增量
合并  ：客户端三方合并  →  按域判定冲突  →  服务端权威合并（按需）
```

## 四、阶段路线

| 阶段 | 版本位 | 主题 | 出口条件 |
| --- | --- | --- | --- |
| A | v2.8.7 | 提交瘦身 | 平均提交字节数下降 ≥50%；no-op 提交归零；一次编辑动作 ≤1 次写；旧客户端零回归 |
| B | v2.8.8 | 域级版本 | 跨域并发 409 归零；三方合并调用次数显著下降；无 `baseRevisions` 的旧客户端仍走整行 CAS |
| C | v2.9.x（并行） | 记录级写 + 增量读 | 单记录改动只推进该记录版本；增量拉取命中率可观测；写槽 429 归零 |
| D | v3.0.x（按需） | 服务端权威合并 | 触发条件：出现多人同时编辑同一域，或教室端需要写回 |

### 阶段 A：提交瘦身（本次落地）

范围：**不改协议形状、不改读契约、不动 outbox/三方合并语义**，只让提交内容变小、无变化不发请求。

- A1（服务端）`exam_data` 写入改为「携带才覆写」：`items`/`title`/`majors`/`activeMajorId`/`alerts`
  由无条件覆写改为按字段存在与否决定，其余域保持既有 `COALESCE` 语义；集中到一个纯函数里判定。
- A2（服务端）请求校验从「必须带 `items`」改为「至少携带一个可写域」，保留 `items` 非法的 400。
- A3（服务端）`validateMutation` 改为省略安全：未携带的域一律按服务器当前值参与比对，
  避免「只发周测」被误判成「删光了所有大型考试」。
- A4（客户端）提交前与服务端基线快照按域比对，只发变化域；无变化直接视为已保存，不发请求。
- A5（客户端）镜像字段一致化：`items`/`title` 与 `majors[activeMajorId]` 一起判定为同一组，
  该组未变化时不发。
- A6（可观测）记录每次提交的变化域名与字节数，作为阶段 B/C 的决策依据。

明确不做（A 段）：不拆表、不改 ETag、不改 409 语义、不改 outbox payload 结构。

### 阶段 B：域级版本

- B1 `exam_data` 增 `revisions JSONB`（`majors`/`weekly`/`schedule`/`grades`/`classes`/`alerts`/`initialization` 等各一个自增号）。
- B2 请求带 `baseRevisions`，服务端只对**同域**被并发修改返回 409，且只回冲突域。
- B3 `updated_at` 继续作为文档版本（ETag 与边缘缓存语义完全不变）。
- B4 兼容：无 `baseRevisions` 的请求走现有整行 CAS。

#### B 段落地中的关键约定（2026-09-25 实施后补记）

- **修订域 ≠ 保存域**：`items`/`title` 永远跟着 `majors` 走，周测计划与「哪份计划生效」同属一次编辑，
  所以 13 个保存域归并成 7 个修订域（`major`/`alerts`/`weekly`/`schedule`/`grades`/`classes`/`initialization`）。
  两者必须一一覆盖，由单测锁定，漏一个域就等于该域没有并发保护。
- **修订号只在值真的变化时 +1**：判定放在 SQL 里用 `IS DISTINCT FROM` 读更新前的旧值，
  所以「把同一个域原样再提交一次」不会平白制造别人的冲突，也不需要额外的读往返。
- **「缺字段」与「全是 0」语义不同**：客户端带 `baseRevisions` 表示「我按域比较」，
  表里没有的域按 0 处理；客户端根本不带该字段（老客户端/老快照/老服务端）则退回整行 `updated_at` 比较。
  这条区分是跨版本部署时唯一的保护，不能合并成一种情况。
- **所有写快照的路径都要推进修订号**：主保存路径、自动开考/结束（`examAutoLifecycle`）、
  记录层生命周期动作（`examRecordRoutes`）、数据重置（`settingsRoutes`）。少一处，
  携带 `baseRevisions` 的客户端就可能覆盖掉那条路径写入的状态。
- **客户端的基线只按「本次提交过的域」推进**：其余域的本地内容仍基于旧版本，
  跟着换成服务端的新号会变成静默覆盖。
- 待办：409 响应目前仍回整份 `remote`（另附 `conflicts` 与 `revisions`），
  「只回冲突域」留作后续优化，客户端三方合并逻辑因此无需改动。

### 阶段 C：记录级写 + 增量读

- C1 周测计划、年级/班级按 `exam_records` + `exam_record_operations` 已验证的范式建记录表
  （`version` + `idempotency_key` + 状态机），先周测后班级。
- C2 命令接口：`upsert(recordId, patch, baseVersion)` / `delete(recordId, baseVersion)`。
- C3 快照降级为投影，读取新增 `since=revision` 增量拉取；整份读取保留。
- C4 全局 900ms 写槽改为按域（或按资源）令牌桶，去掉跨域互相排队。

### 阶段 D：服务端权威合并（按需）

- D1 新增 `exam_data_revisions`（snapshot / updated_at / actor_id / changed_domains），保留最近 N 个快照。
- D2 冲突时由服务端完成三方合并，客户端只负责重试；顺带获得版本时间旅行与审计能力。
- 触发条件不足时不做。

## 五、数据模型演进要点

- `revisions` 与 `updated_at` 并存：前者做冲突判定，后者做兼容版本号。
- 记录表沿用既有命名与语义（`version`、`idempotency_key`、`created_by`、`updated_at`），不另创范式。
- 新域准入三条：改动是否总是局部的？频率是否足够高？是否有稳定主键与版本？三条都满足才关系化。
- 快照投影必须可重建：任何记录表都要有从快照回填的幂等脚本（对应 v2.8.0 已有做法）。

## 六、兼容与迁移

每个域走「双读 → 双写 → 切权威」三步，任何一步都能停：

1. 双读：新旧读路径并存，返回值必须一致（用同一组夹具对比）。
2. 双写：写路径同时更新记录表与快照，以快照为准。
3. 切权威：记录表为准，快照由投影生成。

分流规则：无 `baseRevisions` 走整行 CAS；无 `since` 返回整份；`action=initialize`、重置、测试数据导入一律整份提交。
迁移脚本必须空库、旧库、重复执行三种情形都通过，回滚不丢数据。

## 七、可持续性看板

阶段 A 起开始采集，作为后续阶段的判据：

| 指标 | 用途 |
| --- | --- |
| 单次提交字节数 p50/p95 | 提交瘦身是否达标 |
| 每分钟写请求数、429 计数、写槽等待 | 写入节流是否仍是瓶颈 |
| 409 率、三方合并次数、`conflictCount` 分布 | 冲突粒度是否真的变细 |
| GET 304 命中率、增量拉取命中率 | 读取侧收益 |
| outbox 积压时长、`max-retries` 次数 | 离线能力健康度 |
| 客户端版本分布、错误率 | 已由遥测覆盖 |

## 八、测试与门禁

- 纯函数单测覆盖新增判定逻辑（变化域计算、省略安全校验），不依赖数据库。
- 集成测试扩展真实库并发场景：由「并发写同一行」扩到「并发写不同域」，断言互不冲突（阶段 B 起）。
- 旧客户端兼容回归：整份提交、无 `baseRevisions`、无 `since` 三条路径必须有断言。
- 会话内 `npm run verify:fast`；push 前 `npm run verify:full`；CI 兜底（既有约定）。

## 九、风险与不做清单

风险：

- 共享工作树上有并行会话，改动 `examDataRoutes`/`examService` 前先确认无并行修改同一文件。
- Vercel 公开函数数量上限 12：新增入口必须走合并入口 + `vercel.json` rewrite（参考 2026-09-24 修复）。
- Neon 免费额度下**写次数**是稀缺资源：优化目标是减少无意义写，而不是把一次写拆成多次。
- 提交变小后，服务端「未携带则保留」的语义必须与客户端 diff 完全一致，否则会出现静默丢字段；两侧共用同一份纯函数与夹具来锁定。

不做：

- 一次性把协议改成纯增量（op log + 重放 + 离线合并重做），成本最高且收益与 A/B 重叠。
- 引入 CRDT，或把 `majors` 拆成逐条请求。
- 让读侧变增量（教室端与插件会直接失效）。
- 在没有指标证明需要时启动阶段 D。

## 十、节奏

1. 第一批次：阶段 A（A1–A6），单会话可完成，跑 `verify:fast` + 旧客户端兼容回归，产出字节数与请求数前后对比。
2. 第二批次：阶段 B，按第一批量到的 409 分布决定是否调整域划分。
3. 第三批次：阶段 C 分域推进（先周测，后班级）。
4. 阶段 D 保持「有触发条件才启动」。

每个批次完成后按仓库既有约定更新 `task_plan.md`、`findings.md`、`progress.md`，
并把阶段任务状态同步回 `novora-version-tasks.md`。
