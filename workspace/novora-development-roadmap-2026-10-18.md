# Novora 开发计划表（基于 2026-10-18 现状）

> 当前路线草案。v2.8.1 文件与规则见 [开发入口](../docs/2.8.1/README.md)，阶段 A 的逐项执行与发布门禁见 [收尾检查表](../docs/2.8.1/RELEASE-CHECKLIST.md)。后续阶段的存储、阈值和打包形式仍需专项设计，不代表已实现。

## 1. 基线判断

当前主项目是 `v2.8.1` 开发线，已经不是旧路线文档里的 v2.7.3 状态。现有能力可以归为：

| 能力 | 当前状态 | 证据位置 | 判断 |
|---|---|---|---|
| 网页版考试与学校管理 | 已实现 | `src/`、`api/_exams/`、`README.md` | 已有可用基础，继续收尾和稳定 |
| 本地/内网学校服务端 | 已实现基础版 | `server/`、`DEPLOY_LOCAL.md`、`docker-compose.yml` | Node + PostgreSQL + Docker 可部署 |
| Windows 学校部署 | 已实现基础版 | `packaging/windows/` | 有自包含安装器、服务、控制中心和备份 |
| 教室客户端 | 已实现 | `src/`、离线 outbox、设备绑定、公告、时间同步 | 当前是浏览器/PWA 形态 |
| 设备身份、心跳、命令 | 已有第一版 | `api/_exams/routes/device*`、`device_commands` | 只能支撑低频轮询命令，尚未成为 Agent 协议 |
| 公告与已读回执 | 已实现 | `exam_announcement*`、公告组件与迁移 | 可复用到多教室版 |
| 错误和诊断上报 | 已实现基础链路 | `src/services/errorReport.ts`、`diagnosticLogs.ts`、作者端仓库 | 需要产品化开关和文档收口 |
| ClassIsland 插件 | 已实现 API v2 配对与同步 | `integrations/ClassIsland.ExamReminder/` | 先稳定协议，再接 Agent |
| 作者端 | 已有独立项目 | `exam-board-telemetry-author/` | 已有错误、诊断、版本和实例相关接口 |
| 单教室版 | 未形成独立产品 | 目前只能通过 PWA/本地服务组合 | 需要运行模式和功能裁剪 |
| 多教室版完整空间管理 | 未完成 | 设备表已有，空间模型仍是后续任务 | 需要学校、校区、楼、层、教室闭环 |
| 独立 Agent | 未实现 | 当前无独立 Agent 工程 | 不能把 Windows ServiceHost 直接当 Agent |
| 网页考试码连接 | 未实现 | 当前主要是账号/插件配对 | 需要 ExamSession/EnrollmentToken 协议 |
| Linux 原生安装包 | 未实现 | 当前主要是 Docker/Node 部署 | 先支持 Linux 服务部署，再考虑发行包 |

## 2. 产品边界

对外仍按六个产品入口规划，技术上按部署单元拆开：

| 产品入口 | 技术部署单元 | 当前主项目关系 |
|---|---|---|
| 网页版 | 云端 Web + API | 直接复用现有 Vercel/Neon 体系 |
| 多教室版服务端 | 学校 Linux/Windows 服务 | 复用 `server/`、PostgreSQL 和现有 API |
| 多教室版教室客户端 | 每间教室的 Web/PWA 或桌面启动器 | 复用现有教室端，增加运行模式 |
| 单教室版 | 本机持久化数据 + 可选作者上报（存储选型待验证） | 从教室端裁剪功能，不另起一套前端 |
| Agent | Windows Service / Linux systemd | 新增独立后台进程，共享设备和命令协议 |
| ClassIsland 插件 | ClassIsland 插件包 | 复用现有 API v2，逐步接入 Agent |

作者端是平台服务，不单独计入用户端数量；它负责版本、错误、诊断和公告，不读取学校考试正文。

## 3. 执行顺序

### 阶段 A：v2.8.1 收尾与发布基线

**目标：** 把当前已有功能变成可重复发布的稳定版本。

| 编号 | 任务 | 范围 | 状态 | 出口条件 |
|---|---|---|---|---|
| A-01 | 完成 v2.8.1 当前分支合并和变更记录 | 全端 | 进行中 | 主项目、作者端、插件的版本关系明确 |
| A-02 | 完成考试闭环回归 | 网页版/教室端 | 待执行 | 创建→编辑→发布→显示→控制→结束→归档→复制通过 |
| A-03 | 完成离线 outbox、ETag、域级版本回归 | 网页版/教室端 | 待执行 | 断网编辑不丢数据；旧客户端仍可读写 |
| A-04 | 完成设备命令状态机测试 | 服务端/教室端 | 待执行 | pending、acknowledged、expired、failed、幂等均有测试 |
| A-05 | 作者端错误、诊断、实例上报文档收口 | 作者端 | 待执行 | 上报开关、脱敏、失败重试和数据保留策略写入文档 |
| A-06 | 发布质量门禁 | 全端 | 待执行 | `verify:full`、真实 PostgreSQL 集成测试、Windows smoke 通过 |

**阶段出口：** v2.8.1 可以作为稳定基线，后续功能不再建立在未验证的同步和设备命令上。

### 阶段 B：v2.9 设备和空间基础

**目标：** 先把“学校里有哪些教室电脑”管理清楚，再开发 Agent。

| 编号 | 任务 | 范围 | 状态 | 出口条件 |
|---|---|---|---|---|
| B-01 | 设备身份规范化 | 教室端/服务端 | 部分已有 | 设备 ID 刷新不变、可撤销、可重新绑定 |
| B-02 | 空间模型 | 学校服务端 | 待开发 | School→Campus→Building→Floor→Room→Device 可增删改查 |
| B-03 | 设备注册与绑定向导 | 服务端/教室端 | 部分已有 | 管理员能生成绑定码，教室端能完成绑定和解绑 |
| B-04 | 心跳和状态计算 | 服务端/教室端 | 部分已有 | 服务端计算在线、离线、异常；当前共享契约在线窗口为 180 秒，后续阈值调整须连同心跳间隔和测试验证 |
| B-05 | 学校设备总览 | 学校管理端 | 待开发 | 按校区、楼栋、楼层、教室筛选设备和版本 |
| B-06 | 本校错误中心 | 学校服务端 | 部分已有 | 错误按设备、指纹、级别、版本聚合 |
| B-07 | Linux 服务部署说明 | Linux 服务端 | 待开发 | Docker + systemd 两种部署路径可重复验证 |

**阶段出口：** 一所学校可以完成设备登记、教室归属、在线监控和错误定位。

### 阶段 C：单教室版 MVP

**目标：** 先交付不需要学校服务端的实用版本，保持大部分功能离线。

| 编号 | 任务 | 范围 | 状态 | 出口条件 |
|---|---|---|---|---|
| C-01 | 增加 `single-classroom` 运行模式 | 客户端 | 待开发 | 首次启动可选择单教室模式，模式可持久化 |
| C-02 | 本地数据层 | 客户端 | 部分已有 | 课表、考试、提醒、显示偏好本地可用 |
| C-03 | 单教室功能裁剪 | 客户端 | 待开发 | 隐藏学校结构、多设备、校内公告、复杂权限 |
| C-04 | 作者上报设置 | 客户端/作者端 | 部分已有 | 错误和匿名统计默认可配置，用户可关闭 |
| C-05 | 离线上报队列 | 客户端 | 待开发 | 网络恢复后重试；不影响看板主业务 |
| C-06 | Windows 单教室安装包 | Windows | 部分已有 | 一键安装、开机启动、卸载保留本地数据 |

**阶段出口：** 没有服务器时，单台教室电脑可以独立完成考试提醒；联网只用于作者错误、统计和公告。

### 阶段 D：考试码和网页版连接

**目标：** 让用户在网站上创建考试，教室设备输入考试码即可连接。

| 编号 | 任务 | 范围 | 状态 | 出口条件 |
|---|---|---|---|---|
| D-01 | `ExamSession` 数据模型 | 云端/学校服务端 | 待开发 | 考试定义和设备会话分离 |
| D-02 | `EnrollmentToken`/考试码 | 网页版 API | 待开发 | 6–8 位短码、过期、撤销、使用次数限制 |
| D-03 | 设备输入考试码页面 | 教室端/单教室版 | 待开发 | 输入后显示考试名称、范围和有效期供确认 |
| D-04 | 设备凭证换取 | 云端 API | 待开发 | 密码不落设备；设备使用可撤销的长期凭证 |
| D-05 | 断网缓存 | 教室端 | 待开发 | 连接成功后断网仍可显示已下载考试 |
| D-06 | 连接状态和撤销 | 网页版/服务端 | 待开发 | 管理员可查看、踢出、重新连接设备 |
| D-07 | 防滥用 | API | 待开发 | 码尝试限流、一次性令牌哈希存储、审计记录 |

**阶段出口：** 新用户不部署服务器即可完成“网站创建考试→教室输入码→显示考试”的闭环。

### 阶段 E：Agent v1（先 Windows）

**目标：** 为看板提供可靠的本机自动化入口，先做低风险动作。

| 编号 | 任务 | 范围 | 状态 | 出口条件 |
|---|---|---|---|---|
| E-01 | 独立 Agent 工程和安装器 | Windows | 待开发 | Windows Service、自启动、崩溃重启、日志可查 |
| E-02 | Agent 注册密钥 | Agent/服务端 | 待开发 | 生成、绑定、撤销、重新绑定完整 |
| E-03 | 本机 IPC | Agent/客户端 | 待开发 | Named Pipe 或 localhost WebSocket，带版本握手 |
| E-04 | 出站心跳 | Agent/服务端 | 待开发 | Agent 与看板设备状态分开记录 |
| E-05 | L1 命令 | Agent/服务端 | 待开发 | 刷新、重新同步、显示消息、打开看板页面 |

### 阶段 G：长期平台化

| 主题 | 开始条件 | 内容 |
|---|---|---|
| Agent Linux 版 | Windows Agent 连续稳定 | systemd、权限模型、同一命令协议 |
| L2/L3 命令 | L1 审计和撤销稳定 | 重启 Agent/看板；关机等高风险操作默认关闭并二次确认 |
| 多学校 SaaS | 单校数据边界和授权稳定 | 租户隔离、订阅、学校实例管理 |
| 智能诊断 | 有真实运行数据 | 规则引擎、趋势分析、诊断建议 |
| 深度楼控/考务 | 明确商业需求后 | 不提前进入当前主线 |

## 4. 当前开发优先级

接下来按下面顺序开发，不建议同时启动四条大型新线：

1. **先完成阶段 A**：把 v2.8.1、同步、设备命令和发布门禁锁住。
2. **再完成阶段 B**：设备和空间模型是多教室版、Agent、统计的共同前置。
3. **并行做阶段 C 的单教室 MVP**：它可以最大程度复用现有客户端，最快形成新产品。
4. **随后做阶段 D 考试码**：这是网页版免部署模式的核心卖点。
5. **最后启动阶段 E Agent**：Agent 依赖稳定设备身份、心跳、命令和权限协议。
6. **阶段 F 才做学校级批量运维**：不要在 Agent 和空间模型未稳定前承诺远程控制。

## 5. 每个阶段的固定验收门禁

- 前端/API 改动：`npm run verify:fast`。
- 提交或发布前：`npm run verify:full`。
- 数据库迁移：空库、旧库、重复执行、回滚、并发写各一组测试。
- Windows：控制中心和安装器 smoke test。
- Linux：Docker 部署、systemd 部署、备份恢复各一遍。
- 离线功能：断网、重连、重复提交、队列失败和恢复必须有记录。
- 远程命令：权限、签名、过期、幂等、回执、撤销必须全部验证。

## 6. 不纳入当前开发周期

- 考生账号、报名、座位、监考排班、题库、阅卷和成绩。
- 任意远程 Shell、默认启用的关机/重启等高风险命令。
- 作者端读取学校考试正文。
- 在单教室版中保留完整学校管理、校内公告和多设备功能。
- 同时维护一套独立的单教室前端和多教室前端。
