# Novora 未来项目计划（基于 v2.7.3）

**计划性质**：架构与产品路线草案，不代表已实现功能。

**基线**：`novora-remote-audit` 中的 Novora v2.7.3 快照。工作区中的 `work/Novora` 为旧的 v2.5.6 副本，不作为本计划的实现依据。

## 总体判断

Novora 的主线应保持为：

```text
学校考试安排 → 学校服务端 → 教室大屏/客户端 → 设备运行状态 → 学校内运维
```

作者端只负责 Novora 自身的版本、运行质量和授权运维数据，不承载学校考试正文。Agent 是设备控制组件，不是第四个业务端。

路线可行，但必须先补齐数据模型、命令可靠性和权限边界。版本号不应先于前置条件；每一阶段以验收条件决定是否进入下一阶段。

## 三端边界

### 客户端 Client

- 教室大屏、考试/周测显示、离线缓存和本地显示偏好。
- 设备实例注册、心跳、同步状态和有限的页面级控制。
- 只上传经过同意的必要遥测/错误信息。
- 不负责系统级更新、关机、硬件诊断或跨学校管理。

### 学校服务端 School Server

- 学校、年级、班级、考试、周测、账号、权限和审计。
- 客户端同步、设备绑定、设备运行态势和学校内命令队列。
- 支持 Vercel/Neon 和本地 Node/PostgreSQL 两种部署。
- 学校业务数据留在学校服务端，不同步到作者端。

### 作者端 Author Center

- Novora 实例注册、版本信息、公告、遥测和错误聚合。
- 作者人员的权限、数据保留、脱敏和运维审计。
- 默认只读观察；任何进入学校设备的操作都必须由学校授权并可撤销。
- 不直接编辑学校考试、班级或用户数据。

### Agent（组件，不是业务端）

- 运行在教室电脑上的本地服务，作为学校服务端与操作系统之间的受控执行层。
- 第一版只做 Windows 内测，先支持心跳、页面刷新、重新同步和回执。
- Linux、系统级操作、自动更新和硬件诊断必须在 Windows 版本稳定后再做。

## 分阶段路线（三端并行，v2.7.x → v4.0+）

详细任务清单见 `novora-version-tasks.md`。每个版本包含客户端、学校服务端、作者端三条并行轨道。

### v2.7.x 稳定与质量

修复 Hook 依赖和同步正确性；建立独立数据库集成门禁和 schema 版本记录。

### v2.8.x 考试管理基础

- **服务端**：新增 `ExamRecord` 关系模型 + 生命周期状态机（DRAFT → PUBLISHED → WAITING → RUNNING → FINISHED → ARCHIVED）；`exam_data` 保留为运行投影；考试管理列表/详情/历史/复制；统一操作 API（start/pause/resume/extend/end）+ 操作日志。
- **客户端**：考试管理首页、详情页、控制面板、历史筛选、公告下发、状态异常提示。
- **作者端**：基础实例概览（版本/在线/客户端数），不含考试正文。
- **不做**：考生账号、报名、座位、监考排班、题库、阅卷、成绩、楼控、Agent、远程控制。

### v2.9.x 设备与错误体系

- **客户端**：设备 ID（`NOVORA-XXXX-NNNNNN`）、定期心跳、本地日志中心。
- **服务端**：`Device` 表 + 空间模型种子（School → Campus → Building → Floor → Room → Device）；服务端判定在线/离线/异常；学校错误存储（指纹去重）。
- **作者端**：错误中心（Critical/Error/Warning/Info 分级，跨实例聚合）；实例级日志摘要（脱敏）。

### v2.10.x 作者中心正式版

- **作者端**：独立服务（与学校服务端隔离部署，不共享数据库）；实例管理、版本中心、更新包管理。
- **服务端**：版本检查 API、更新下载 API、实例定期上报。
- **客户端**：更新提示 UI、更新执行流程。

### v2.11.x 远程诊断与授权

- **作者端**：诊断面板、诊断报告导出、授权验证、远程日志查看器。
- **服务端**：学校管理员授权流程（授权码/有效期/撤销）、诊断数据 API（脱敏）、日志推送。
- **客户端**：授权状态显示。

### v2.12.x Agent 组件

- **Agent**：Windows 服务（自启动/崩溃重启）→ Linux systemd；出站连接和心跳；设备注册密钥。
- **命令分级**：L1 页面控制（刷新/切换/同步/消息）→ L2 系统控制（重启 Agent/看板/更新/清缓存）→ L3 高风险（关机/重启/电源，必须确认，默认禁用）。
- **服务端**：Agent 注册 API；命令签名/过期/幂等/审计。

### v3.0.x 平台化 + 态势

- **服务端**：空间模型完整（校区/楼/层/教室 CRUD + 设备归属）；统一考试状态计算服务。
- **客户端**：教学楼可视化、设备归属显示、考试态势主界面（当前考试/设备统计/下一场/运行事件）；态势与楼控分离。
- **作者端**：平台统计（脱敏聚合）。

### v3.1.x 远程考试发布 + 广播

- **服务端**：远程发布 API、消息 API、广播管理（模板/目标/定时/历史）。
- **客户端**：远程接收考试、大屏消息显示（不遮挡倒计时）。
- **作者端**：广播模板库。

### v3.2.x 学校运维中心

- **服务端**：运维 API（批量操作/日志导出/配置下发）、自动更新策略。
- **Agent**：自动执行更新（下载/安装/重启）。
- **作者端**：灰度发布（按百分比/设备列表/学校列表）、灰度回滚。

### v3.3.x 智能诊断

- **服务端**：诊断规则引擎（基于日志/心跳/错误模式判断异常）。
- **作者端**：AI 分析（错误趋势/根因推测/建议）、诊断仪表板。
- **客户端**：诊断建议展示（非侵入）。

### v4.0+ 综合平台

多学校管理、商业化授权/计费、楼控深度（空调/灯光/门锁）、考务系统（考生/考场/监考/成绩）、AI 助手、开放 API。按需拆版本。

## 关键技术决策

1. **先管理元数据，再改运行快照**：避免把 `exam_data` 单行 JSONB 直接改成破坏性新模型。
2. **学校服务端是业务数据边界**：作者端只收运行所需的最小数据。
3. **轮询心跳不等于实时控制**：现有心跳可支撑状态展示和低频命令，不能宣称实时双向通道。
4. **浏览器随机实例 ID 不等于可信设备身份**：Agent 阶段必须引入注册密钥、撤销和恢复机制。
5. **先 Windows 再 Linux**：减少同时面对安装、权限、服务管理和网络差异的风险。
6. **Agent 是客户端侧组件，不是第四个产品端**：安装在教室电脑上的本地服务，增强远程运维能力。
7. **三端职责固定**：客户端负责显示和执行；学校服务端负责学校业务和设备管理；作者端负责软件生命周期和运维。作者端不读学校考试正文。
8. **远程控制必须分级**：L1 页面控制（低风险）→ L2 系统控制（中风险）→ L3 高风险（必须确认，默认禁用）。

## 当前明确的不可行/不应承诺项

- 在不新增作者后台、授权协议和命令队列的情况下，实现跨学校远程控制。
- 仅靠浏览器客户端实现可靠的关机、重启、显示器检测和系统更新回滚。
- 仅增加 `exam_records` 表而不处理现有 `majors`、离线 outbox、ETag 和并发写入。
- 在没有空间模型和真实设备归属数据时交付可用的教学楼地图。
- 在没有真实运行数据和安全审计的情况下上线 AI 批量操作或商业化远程运维。

## 计划维护规则

- 每个版本先写数据/API 契约和出口条件，再拆 UI 任务。
- 每完成一个阶段，更新 `task_plan.md`、`findings.md`、`progress.md`。
- 新发现必须记录证据、影响和置信度；错误不得静默重试。
- 任何跨学校数据、远程操作或系统级命令都需要单独的隐私/安全评审。
