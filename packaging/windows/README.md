# Novora Windows Installer

The Windows release is a self-contained x64 installer. School computers do not need Node.js, PostgreSQL, Docker, .NET, or the Visual C++ runtime installed. The installer payload includes the Novora production dependencies, Node.js runtime, PostgreSQL 16 binaries, Visual C++ Redistributable, and a self-contained Windows Service host.

## Build

Run from the repository root on a Windows x64 build machine with Node.js 24, .NET 8 SDK, PowerShell 5.1+, and Inno Setup 6 installed:

```powershell
npm run windows:package
```

The build downloads pinned Node.js and PostgreSQL binary archives, builds Novora, the Windows Service host, the tray app, and the Windows launcher, stages production-only dependencies, and invokes Inno Setup. The release version has one source: `package.json`. `build.ps1` reads it, stamps it into the staged `operation-progress.ps1` (the marker line is `$script:NovoraProductVersion`; a staged copy without exactly one marker fails the build) and passes it to Inno as `/DAppVersion`, so `Novora-Setup-<version>.exe` is written under `artifacts/windows/installer`. `Novora.iss` refuses to compile without `/DAppVersion`, and scripts read the version from the payload (`active-version.json`, then `package.json`, then the stamped value) instead of a literal. First PostgreSQL archive is about 320 MB, so the final installer is large; later builds reuse valid downloaded archives.

The release builder requires internet access. The resulting installer itself is offline: it contains all application runtimes and only needs Windows during installation.

## Install behavior

- Installs program files in `C:\Program Files\Novora` and school data in `C:\ProgramData\Novora`.
- Deploys the bundled PostgreSQL binaries. Initialization prepares a private instance on `127.0.0.1:55432`; this does not use or modify any other PostgreSQL role or database on the machine.
- The installer does not create database configuration, initialize a cluster or register services. Initialization invokes `provision-services.ps1` to prepare configuration, data-directory permissions and both Windows services, then applies the selected startup policy and starts/verifies them.
- Initialization can open the selected HTTP port (default `3000`) for every Windows firewall profile, with inbound traffic limited to the local subnet. PostgreSQL is not exposed to the LAN.
- Initialization creates an initial administrator password when none is provided and saves it in the administrators-only `config\initial-credentials.txt` file.
- Preserves the data directory during normal uninstall. Database removal is a separate explicit action. Cleanup no longer fails silently: a remaining firewall rule, shortcut, Start-menu or `-PurgeData` data directory is listed with its reason (file in use or access denied) and uninstall ends with a nonzero exit code. `uninstall.ps1` closes its own transcript before deleting data, otherwise the log handle keeps `ProgramData\Novora` undeletable.

## Installation progress and failure handling

File deployment uses the Inno progress bar. Upgrade stop preparation, runtime installation, base directory preparation, shortcuts and removal use `install-runner.ps1`, with the current item, elapsed time, a progress bar and failure actions. Unknown durations remain indeterminate; service waits and probes report their deadlines. The runner offers retry of the failed step and a log-folder action. Silent setup returns a nonzero exit code without launching initialization when a required step fails.

PostgreSQL configuration is written as UTF-8 without BOM, including repair of an earlier BOM on an existing Novora cluster. So are `.env`, `initial-credentials.txt`, `runtime.json`, `windows-initialized.json`, the initialization result file and the runtime check log (`runtime-check.log` is appended through `File.AppendAllText`, never `Add-Content -Encoding UTF8`): `Write-NovoraUtf8File` writes them via .NET because Windows PowerShell 5.1 adds a BOM to `Set-Content -Encoding UTF8`. `initial-credentials.txt` keeps its Chinese labels as UTF-8 (never an ASCII fallback). Scripts themselves must keep their UTF-8 BOM: Windows PowerShell 5.1 decodes a BOM-less script with the ANSI code page, and the shared helpers contain Chinese labels. Initialization provisioning preserves `PG_VERSION`, school data, existing passwords, ports and operator-owned PostgreSQL tuning. Registration paths are checked before stopping a same-named service; the installer does not manage the machine's independent 5432 instance. Existing Novora registration is updated in place. A full installer refuses to overwrite an installation with an active application-version pointer or a root package newer than its own injected product version; those cases require a dedicated full-upgrade flow. A payload whose product version was never injected refuses the check instead of assuming a release.

Installation completes after base file deployment and shortcuts. `install.ps1` only checks installation ownership and update boundaries, prepares directories, safely stops owned old services, and — when run by hand with the tray or the wizard enabled — starts them through the desktop shell so neither inherits its administrator token. It does not write `.env`, initialize a database cluster, register services, run `postgres.exe -C`, start services, connect to SQL, create the application database or wait for HTTP. Initialization invokes `provision-services.ps1` before applying settings. New PostgreSQL services use Windows `New-Service` with a quoted `pg_ctl.exe runservice -N ... -D ... -w` command and the NetworkService account, avoiding the `pg_ctl register` child-process wait and subsequent service configuration permission failure. Existing matching services are updated in place; ownership/account mismatch or denied management access fails visibly without changing service DACLs. Initialization starts PostgreSQL through SCM under its service account, verifies the actual SQL role/port/data directory, creates `novora` idempotently, starts Novora and requires `/api/health` to report `ok=true` before recording completion. Completion, `windows-initialized.json.completed`, the result file's `ok` and the exit code follow the fatal checks only: a service that cannot run, an unusable database, a missing required file or an invalid port/configuration throws, exits nonzero and leaves the stored completion at `false`. Anything else is recorded in `warnings`, is still shown item by item in the control center, the tray flow and `initialize.log`, and does not invalidate an otherwise healthy initialization — a refused service start-mode write, for example, keeps the registered service and its current start mode. Partial application errors include the completed items; missing services and SCM failures cannot be recorded as a successful initialization.

Installation, initialization, uninstallation, service operations, backup/restore and application updates share `Global\Novora.DatabaseMaintenance`. Inno holds it throughout file deployment. An unfinished update that requires recovery blocks installation and service changes until recovered in Windows settings. Backup and restore go through the same gate before touching the database, and restore keeps the lock for its safety backup and transaction.

The Windows Service host refuses to start while `updater\state.json` reports an unfinished update phase that needs recovery, and the SCM failure text names that phase and points at Windows settings; `verifying` and `rolling-back` stay startable because the updater starts the service itself at exactly those phases to check the new or restored version. Service output is written by a single background writer that drains its queue in batches of up to 512 lines, so concurrent stdout and stderr can neither lose nor reorder lines, and `novora-service.log` rotates at 5 MiB keeping three archives (`.1` newest, `.3` oldest). A failed log write never reaches the service: the writer carries on with the next batch after a 200 ms back-off, and service stop drains the queue for at most five seconds.

## First-run experience

- The installer creates desktop and Start menu shortcuts that point at `NovoraLauncher.exe`, plus a tray shortcut in the per-user Startup folder.
- The installer starts the launcher once at the end of setup with the interactive user's token (`runasoriginaluser` on the finish-page entry); later, the desktop icon opens it. Setup started from an already elevated process keeps that administrator token through `runasoriginaluser`, so `launch-setup.ps1` detects the elevation and hands the wizard to the desktop shell through a temporary shortcut instead of leaving the control center running as administrator. If no desktop shell of the current session is available, it starts the wizard directly as before.
- Elevation never reaches a long-lived UI. `initialize.ps1` runs elevated for the settings themselves but does not start the tray as a child of that process: it hands the Startup-folder shortcut it just created to the desktop shell (`Start-NovoraShellShortcut` in `operation-progress.ps1`). A manual `install.ps1` run does the same for the tray and the initialization wizard through `Start-NovoraUserInterface`, which writes a fixed per-entry-point shortcut under the user's temp directory because `explorer.exe` ignores arguments appended after a target path. When the session has no desktop shell, both fall back to a direct start and record a non-fatal warning.
- The launcher is a .NET 8 WPF control center with six left-hand destinations: overview, a four-step initialization wizard, Windows settings, software updates, service logs, and backups. First run checks the machine and asks the operator to review settings before starting and verifying services. Closing or postponing first initialization leaves services unregistered; an existing installation keeps its owned services stopped until initialization is applied.
- Settings only touch Windows-level configuration (service start modes, firewall rule, Startup folder, shortcuts). Novora business settings stay in the web admin UI.
- Completed state is stored in `%ProgramData%\Novora\config\windows-initialized.json`. It is `true` once every fatal check passed; non-fatal warnings are listed separately and keep the update entry points available.
- The tray menu item `系统设置` opens settings using `--system-settings`; `--windows-setup` remains compatible. Left click opens the control center and right click uses the native tray menu.
- All settings are applied by `initialize.ps1` in a single elevation prompt; the launcher itself does not require administrator rights, and neither the control center nor the tray is expected to run elevated.

The current installer targets Windows x64 desktop/server editions. The bundled .NET 8 desktop runtime sets the practical floor at Windows 10 1607 / Server 2016; the installer itself does not gate on the build number, so older systems install but the tray and control center are unsupported there and only expected to stay readable (no icon column, light theme). HTTPS termination, MSI/GPO rollout, and signing remain follow-up work.

## UI resource policy

The new WPF project is `Novora.ControlCenter`; it publishes as `NovoraLauncher.exe` for existing installer and shortcut compatibility. Old launcher projects remain as reference and are not included by the build. No Windows App SDK or browser runtime is required for the control center.

- One window per user session, with same-user named-pipe activation.
- A launch that cannot reach the running instance's activation pipe takes the single-instance lock again (a holder that is exiting abandons it) and opens its own window if the lock became free; if the lock is still held it exits quietly with code 0, because the operator already has a window. It does not report a startup failure for that case.
- A failed activation round is written to the Windows trace output, waits with a 0.5–5 second back-off, and the listener keeps serving later activations; one broken request never disables activation for the life of the process.
- Status refresh every 10 seconds, with overlapping refreshes suppressed and polling paused while minimized. Closing the window ends the control center process; services and the separate WinForms tray continue.
- Health requests have a 3-second deadline including body reading and a 16 KB response limit.
- Logs read at most 128 KB / 300 lines; backups show at most 100 entries using list virtualization.
- Waiting operations show an indeterminate or measured progress bar, current item and elapsed time. Failures keep their details visible and offer logs, a diagnostics summary and retry where safe. Restore/delete require a fresh confirmation for another attempt.
- Page changes use a 120 ms opacity animation and respect Windows animation preferences.
- Visual language is pure WPF with no third-party UI package: `Themes/Tokens.*.xaml` holds the palette and `Themes/Controls.xaml` holds every control template. Controls read tokens through dynamic resources only, so a theme switch repaints the live window. Token keys and style keys share one resource namespace and `DynamicResource` ignores the value type, so a brush named `Skeleton` would satisfy `Style="{DynamicResource Skeleton}"` and throw while the window loads; color tokens therefore carry a `Fill`/`Background`/`Border` suffix.
- Three surface tiers do the separation work instead of shadows: canvas is the darkest step, the navigation rail sits in the middle (`RailBackground`), cards and the selected nav item are the top step with a dedicated `CardBorder` outline.
- Disabled controls switch to a neutral grey fill and `DisabledText` instead of dropping the whole template to 45% opacity, which turned a blue primary button into a washed-out blob that read as a rendering fault. Check boxes keep their tick or mixed dash and only fade the box, because "checked but not clickable" is real state.
- Type scale is page title 22 / section 16 / metric 24 / body 14 / hint 12, with body and hint set to `BlockLineHeight` because WPF text has no leading control and multi-line Chinese collapsed without it. Long sentences use the body style and a capped measure so they stay inside a readable line length; the settings and update columns use `MaxWidth` without a left alignment, which would otherwise shrink the whole column to its content width.
- The overview waits with skeleton bars in the metric cards and the process line instead of four separate "checking…" strings, and the caption carries one status pill (version plus reachability) rather than a bare `v未知`.
- Native WPF parts that ignore the palette are re-templated the same way: the check box (including the mixed/unknown state the inspection step sets while it runs), the scroll bar, and the `GridView` column header, whose stock style is white-on-white in the dark palette.
- Code that picks a semantic colour (update result banners, the channel badge) sets a dynamic reference to a palette key instead of a literal hex value, so a switch between the light and dark palettes repaints it too.
- Light and dark follow the current user's `AppsUseLightTheme` setting, re-checked on the existing 10-second refresh; the registry read is guarded and any failure keeps the light palette. `NOVORA_UI_THEME=light|dark` overrides it for one process, which is how both themes are screenshotted without changing the machine's appearance.
- The window keeps the native title bar: a self-drawn `WindowChrome` shell swallowed the minimize/maximize/close buttons and the Windows 11 snap layouts, and needed a 4 px inset hack when maximized. The branding strip now sits below the system bar as a toolbar (card surface plus a 2 px accent hairline) and the OS title carries the version and reachability (`Novora 控制中心 · v2.8.1 · 运行中`), which also shows in the taskbar and Alt+Tab.
- Cards carry no `DropShadowEffect` (a bitmap effect pushes the whole subtree through the effect pipeline); separation comes from the three surface tiers plus the `CardBorder` outline. Text antialiasing follows the palette: dark mode switches to `TextRenderingMode=Grayscale` because ClearType's subpixel rendering puts red/blue fringes on thin CJK strokes over dark surfaces and reads as blurry even at 100% scaling, while light mode keeps ClearType for edge acuity. `Theme.ApplyTextRendering` sets the inheritable attached property per window, including dialogs opened later.
- Navigation is a left rail with a selected-item border, an icon per destination and a status dot that mirrors the overview verdict. Narrow widths shrink the rail (208 px to 168 px below 1120 effective px) and the default 1280×852 window (taller than the old 820 to pay back the native title bar) is clamped to the work area, so 1366×768 teaching machines still fit.
- Overview leads with a status banner that states the condition and the next action, with start/logs/export shortcuts; the four metric cards carry colored status dots, and service start/restart/stop enable and disable from the observed state instead of failing after a click.
- The wizard shows a four-segment stepper with completed steps checked, and inspection results are ordered blocking-first with a passed/needs-attention/pending count and an optional "only show failures" filter.
- Service logs render as virtualized rows tinted by level with a match count and an empty state; backup actions that need a selection stay disabled until one exists, and an empty backup list shows what to do next. The backup list has a 类型 column taken from the writers' own protection-name contract (`novora-before-update-`, `novora-before-restore-`, otherwise regular), the same prefixes retention uses, so the UI never guesses from an arbitrary file name.
- The inspection step reads current Windows service, firewall, shortcut, initialization, and scheduled-task state. Firewall and scheduled-task lookups use targeted `-DisplayName`/`-TaskName` queries, so no check enumerates every rule or task on the machine; an absent rule or task still reports `未配置` while an unreadable one keeps its warning. Applying changes requires an administrator prompt.
- Daily database backup can be scheduled for 02:00, with 1–365 regular backups retained. Restore first creates a protected backup and uses a single PostgreSQL transaction.
- The tray menu is an owner-drawn card: rounded corners come from DWM on Windows 11 and from a rounded window region on earlier builds, with the shadow left to the system. Colors are read from `Novora.Ui/UiTokens.cs`, which mirrors the control center's `Themes/Tokens.Light.xaml` / `Tokens.Dark.xaml` value for value, and `NOVORA_UI_THEME=light|dark` overrides the choice for that process only; high contrast falls back to system colors. Icons are pre-rendered Segoe MDL2 glyphs, rasterized with GDI+ grayscale antialiasing rather than `TextRenderer` — GDI writes subpixel data into RGB and leaves alpha opaque, which fattens strokes on a light card and tints them blue/orange on a dark one. The icon column collapses when that font is missing (Windows 7/8). The service row carries a green/red status dot and the destructive rows (`停止服务`, `退出托盘`) use the danger color. Keyboard navigation, access keys, screen-edge placement and tooltips stay on the standard ToolStrip path. It reads SCM state separately from HTTP health, disables unavailable/repeated operations and routes backup to the control center. Exiting the tray leaves services running. Service commands share `service-operation.ps1` with the control center.
- The tray right-click menu links directly to overview, initialization, Windows settings, software updates, logs, and backup pages; service start/restart/stop remain available there.
- The taskbar icon's jump list provides the same six page shortcuts (`--overview`, `--windows-setup`, `--system-settings`, `--updates`, `--logs`, `--backups`). Windows shell policy and the user's jump-list settings determine whether those shortcuts are displayed.

## Software updates

Software updates is its own left-hand destination rather than the tail of the Windows settings page, so the initialization wizard can never show it and operators do not have to scroll past the settings form to reach it. See [UPDATES.md](UPDATES.md) for trust, author-service recommendation, signed application packages, offline import, recovery and production activation requirements. Application update code is implemented; the production channel is not enabled by this source change.

The update page groups version/channel status, online check/download/install, offline import, history/cache and optional telemetry into separate cards. Download and install actions appear only for the current stage; result messages explain trust setup, package compatibility, verification, cancellation and recovery. Installation still requires a fresh initialization/service-health check. History shows up to 50 entries with local time, previous/target versions, source and outcome; clearing downloads requires confirmation. Telemetry remains off by default and reports the saved preference. Missing trust disables checking/import without affecting history access.

`build.ps1 -UpdateTrustFile <path>` optionally embeds an issuer-provided `updater/trust.json`. It requires the `PikaNova/Novora` repository, a public key and the fixed HTTPS author endpoint. No private key is generated or included. Omitting trust leaves installation of updates disabled. The build publishes the independent updater into `stage/updater`.

Recommendations use the author service first. GitHub fallback is limited to network failures, timeouts and HTTP 408/429/5xx. An explicit no-recommendation response, signature/identity/version validation failure or HTTP 409 does not trigger fallback. Anonymous update statistics are off by default; when enabled they have a five-second total send deadline and cannot block business operation. Full-setup assets are downloaded and verified for operator review, never silently executed. See the update document for exact activation and recovery boundaries.

## Verification

```powershell
dotnet run --project packaging/windows/Novora.ControlCenter.Tests -c Release
dotnet run --project packaging/windows/Novora.Update.Tests -c Release
powershell -NoProfile -ExecutionPolicy Bypass -File packaging/windows/smoke-controlcenter.ps1 -Executable artifacts/windows/stage/NovoraLauncher.exe
powershell -NoProfile -ExecutionPolicy Bypass -File packaging/windows/smoke-install-runner.ps1
powershell -NoProfile -ExecutionPolicy Bypass -File packaging/windows/smoke-install-progress.ps1 -InstallRoot artifacts/windows/stage
powershell -NoProfile -ExecutionPolicy Bypass -File packaging/windows/smoke-initialize-services.ps1 -InstallRoot artifacts/windows/stage
pwsh -NoProfile -File packaging/windows/smoke-backups.ps1 -InstallRoot artifacts/windows/stage
pwsh -NoProfile -File packaging/windows/smoke-updates.ps1 -InstallRoot artifacts/windows/stage
powershell -NoProfile -ExecutionPolicy Bypass -File packaging/windows/smoke-maintenance-guards-residue.ps1
powershell -NoProfile -ExecutionPolicy Bypass -File packaging/windows/Novora.ServiceHost/verify-servicehost.ps1
```

`smoke-maintenance-guards-residue.ps1` runs on Windows PowerShell 5.1 against a disposable fake InstallRoot/DataRoot with stubbed service control, firewall, Task Scheduler and process APIs. It refuses backup and restore while `updater\state.json` reports an unfinished phase, refuses both while another operation holds the maintenance lock, and checks that uninstall reports locked or denied leftovers and exits nonzero. It never touches the machine's installed instance.

`Novora.ServiceHost/verify-servicehost.ps1` builds its own fixture in a temporary directory (net8.0, no package references, sources compiled in) and asserts the update start gate against the real `UpdateEngine`, then the log writer's batching, ordering, rotation, drain and non-IO failure recovery. It is a source-tree script and is not part of the installer payload.

The UI smoke check requires an interactive Windows desktop and verifies navigation and single-instance activation without applying settings. The activation part now runs before the initialization gate and additionally proves that a page request reaches the running window, that a launch whose activation pipe did not answer exits quietly instead of showing a startup error, that a waiting launch takes over an abandoned lock, and that malformed activation requests leave the listener serving later ones. The backup smoke check uses PowerShell 7, creates and shuts down its own temporary PostgreSQL cluster, mocks Windows service control, and exercises real backup/restore operations; fixtures and logs remain in the printed temporary directory for inspection. Production scripts support Windows PowerShell 5.1. A clean-system install/upgrade/uninstall pass, DPI/accessibility review, and longer installed-service soak test remain deployment acceptance work. Performance numbers are observations on the test machine, not guarantees for every deployment.

The UI smoke needs a *complete* copy of an installed layout, not just the launcher files: the wizard gate inspects `runtime\node.exe` and `postgres\bin\pg_dump.exe` / `pg_restore.exe`, and a self-contained publish needs its runtime DLLs beside it. A trimmed copy fails in two confusing ways — the control center blocks before creating its first window, so the very first activation assertion reports "still running without a window", and the inspection rows blame missing core files. Build `artifacts/windows/stage` by mirroring an installed layout (`robocopy "C:\Program Files\Novora" artifacts\windows\stage /E /R:1 /W:1 /XD pgdata /XF unins000.exe unins000.dat`) and then overwriting `NovoraLauncher.exe`, `.dll`, `.pdb`, `.deps.json`, `.runtimeconfig.json`, `Novora.Update.dll` and `Novora.Update.pdb` from the Release publish directory.

Progress events use `NOVORA_PROGRESS:` followed by one JSON object on stdout, and optionally an atomically replaced snapshot at `NOVORA_PROGRESS_FILE`. Fields are `stage`, `item`, `status` (`running/succeeded/failed`), `current`, nullable `total`, `elapsedSeconds`, `timeoutSeconds`, and `message`. Unknown totals must remain null. Events contain labels and sanitized errors, never credentials or captured database output.

The installation smoke runs under Windows PowerShell 5.1 with a disposable cluster and mocked SCM. It reproduces the BOM failure, repairs it, verifies idempotence/data preservation and rejects database provisioning, registration, SQL, startup, HTTP or direct PostgreSQL configuration probes in the base installation script. It also checks that configuration writes stay BOM-free UTF-8 with Chinese text intact, that the product version is read from the payload (`active-version.json` before `package.json`), that a full installer refuses a downgrade against its own injected version and refuses to guess a version when none was injected. The provisioning fixture supplies its own `NovoraPostgreSQL` registration and startup type instead of reading the machine's, so it never compares against an installed Novora instance. Provisioning checks separately exercise cluster preparation and service-registration command construction. The initialization smoke separately verifies real SQL, database creation and failure handling against a disposable cluster with mocked SCM/HTTP. Neither runs the installer or modifies installed services. The runner smoke replays the same version stamp on its disposable copy of the helper, keeping the BOM that Windows PowerShell 5.1 needs to parse the helper's Chinese labels. The UI smoke walks all six navigation destinations, verifies update actions and disabled missing-trust state on the software-update page, and asserts that update actions are no longer reachable from the Windows settings page. Both light and dark palettes, the maximized frame and the narrow-window rail were checked by screenshot on the test machine rather than by automated assertion. Target-machine install/upgrade/uninstall, real UAC failure and DPI/long-running checks remain required.

Run smoke-initialize-atomic.ps1 under Windows PowerShell 5.1 to exercise both production replacements against disposable files; it also verifies that a denied startup mode stays one non-fatal warning and that completion, the result file and the exit code are never derived from the warning list. Initialization failures now include a redacted script stack in the local log.

The initialization check page shows a summary and individual status rows. Missing services are pending initialization, missing core files block continuation, and unreadable optional settings require an explicit choice later. Checks are on demand with a 45-second limit and retry; the bound covers the one-time ScheduledTasks/NetSecurity module load on cold, dual-core school machines. They do not start services. A refused startup-mode write is a non-fatal warning that preserves the Windows code and points access-denied failures to SCM event 7006 and service/registry protection records; it does not clear initialization completion, and the control center lists it under 需要检查 while still reporting the operation as done.
